## Why this model / review tier
Opus: concurrency-safe claiming on D1 with no interactive transactions. A wrong call here releases PDFs without payment, which the PRD sets at zero tolerance.
Opus review: payments plus core architecture.

## Context
Payments are written by the webhook (`src/lib/db/payments.ts`). Catalog lookup is in `src/lib/db/catalog.ts`. `claimRoutes` is mounted at `/api/claim`. Secrets/vars: `TICKET_SECRET`, `CLAIM_WINDOW_DAYS`, `TOKEN_TTL_HOURS`, `TOKEN_MAX_DOWNLOADS`, `POLL_TIMEOUT_MINUTES`. Turnstile and rate limiting are added in P3-S1-T1; leave a clearly marked hook (`// P3-S1-T1: turnstile + rate limit`) before step 1 of the POST handler. The full algorithm is in `architecture.md` §5 ("Claim algorithm"). Follow it exactly.

## Do this
1. `src/lib/token.ts`: `generateToken()` → 32 random bytes, base64url (no padding); `hashToken(t)` → SHA-256 hex.
2. `src/lib/ticket.ts`: `createTicket(secret, {txn, versionId, expiresAt})` → `base64url(JSON) + "." + base64url(HMAC-SHA256)`; `verifyTicket(secret, ticket, now)` → payload, or null if the signature is bad, the format is malformed, or it has expired. Use `crypto.subtle` HMAC with `verify` (constant-time).
3. `src/lib/claim.ts`:
   - `normalizeTxn(input)`: trim, uppercase, remove all whitespace.
   - `claim(env, {txnInput, versionId, ip, now, origin}): Promise<ClaimResult>` implementing steps 1–9 of the claim algorithm, including:
     - flagging an underpaid payment (`status='flagged'`, `flag_reason='amount_too_low'`, only if currently `unclaimed`) (FR-16);
     - the single `db.batch()` with a fresh `claim_ref = generateToken()` per call; success iff `results[0].meta.changes === 1` (FR-13, FR-14);
     - creating the token with `expires_at = now + TOKEN_TTL_HOURS`, `max_downloads = TOKEN_MAX_DOWNLOADS` (FR-18, FR-19);
     - returning `downloadUrl = origin + "/d/" + token`;
     - writing a `claim_attempts` row with the result code (`OK`, `PENDING`, or the error code).
   - Export `createOrderWithToken(env, {paymentId|null, versionId, createdBy, adminNote, now})` for admin use later (P2-S2-T3). It also uses one batch and returns the raw token. Keep the auto-claim batch separate (it needs the `claim_ref` guard).
   - `ClaimResult = {status:"ok", downloadUrl} | {status:"pending", ticket, retryAfterMs:5000} | {status:"error", code, message}`. Messages are plain English (e.g. ALREADY_USED: "This transaction number has already been used." (FR-17); AMOUNT_TOO_LOW: "The amount received is less than the price. Contact support." ; EXPIRED: "This payment is older than 7 days. Contact support.").
4. `src/routes/claim.ts`:
   - `POST /` → JSON body `{transactionNumber, versionId}` (validate types; 400 otherwise). IP from `CF-Connecting-IP` (fallback `"unknown"`). On `pending`, create a ticket that expires at `now + POLL_TIMEOUT_MINUTES` (FR-15).
   - `GET /status?ticket=` → verify the ticket; invalid → 400 `{status:"error", code:"INVALID_TICKET"}`; expired → `{status:"error", code:"NOT_FOUND", message:"We haven't received this payment yet. Check the number, or contact <SUPPORT_CONTACT>."}` and log one attempt. Otherwise re-run the claim checks and return the same shapes. Pending polls return the **same** ticket and do not write `claim_attempts`.
   - Responses: `Cache-Control: no-store`.

## Acceptance criteria
- Seeded unclaimed 500 ETB payment + 500 ETB version → `ok` with a `/d/<43-char token>` URL; the payment becomes `claimed`; one order (`created_by='auto'`) and one token row with only the hash stored (FR-13, FR-18).
- `" diq55js1ed "` normalizes and matches `DIQ55JS1ED` (FR-12); `"ABC"` → `INVALID_FORMAT`.
- Second claim of the same number → `ALREADY_USED` (FR-17).
- Amount 300 ETB → `AMOUNT_TOO_LOW`, payment `flagged` (FR-16); claiming again → still `AMOUNT_TOO_LOW`.
- `paid_at` 8 days ago → `EXPIRED` (FR-13d); 6 days ago → `ok`.
- Unknown number → `pending` with a ticket; insert the payment, then `GET /status?ticket=` → `ok` (FR-15).
- An expired ticket → `NOT_FOUND`; a tampered ticket → `INVALID_TICKET`.
- **Race:** `Promise.all` of 5 concurrent `claim()` calls for the same payment → exactly 1 `ok`, 4 `ALREADY_USED`, exactly 1 order and 1 token (FR-14).
- Hidden or unavailable version → `INVALID_VERSION`.
- The raw token never appears in the DB.

## Tests to write or update
- `test/claim.test.ts`: every acceptance criterion above (use a fixed `now`).
- `test/ticket.test.ts`: round trip, tampered payload, tampered signature, expired.
- `test/token.test.ts`: length/charset of the token; the hash is deterministic and 64 hex characters.

## How to test manually
1. `pnpm db:reset:local && pnpm seed:local && pnpm dev`
2. Post the sample SMS from P1-S2-T3's manual test (txn `TESTTXN001`).
3. Get the Sealion version id: `pnpm wrangler d1 execute DB --local --command "SELECT id FROM manual_versions"`.
4. `curl -s -X POST localhost:8787/api/claim -H 'content-type: application/json' -d '{"transactionNumber":"testtxn001","versionId":<id>}'` → `{"status":"ok","downloadUrl":"http://localhost:8787/d/…"}`.
5. Repeat → `ALREADY_USED`.
6. `curl … -d '{"transactionNumber":"NOTPAID001","versionId":<id>}'` → `pending` with a ticket. Post an SMS for `NOTPAID001`, then `curl "localhost:8787/api/claim/status?ticket=<ticket>"` → `ok`.
